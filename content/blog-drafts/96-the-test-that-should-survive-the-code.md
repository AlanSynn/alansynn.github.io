# The Test That Should Survive the Code

**Status:** English working draft | **Theme:** L. Software, systems, and engineering judgment | **Candidate tags:** computer-science, philosophy-of-science

Imagine replacing the implementation of a tool with one generated by an agent. The new program is shorter, faster, and easier to maintain. The team keeps a set of tests written for the old program. What should those tests preserve?

Some tests describe behavior that a user relies on. Others describe the internal arrangement of the old implementation. A change to that arrangement may be entirely appropriate. A test that treats it as a requirement can prevent useful changes.

This distinction becomes important when software is revised frequently. A good regression test expresses a relationship the system should continue to satisfy, even when the mechanism used to produce it changes. If a program stores a user's work, a test of whether that work can be recovered matters across many implementations. A test of whether a particular helper function was called may matter only while the current architecture is in place.

There are also cases in which testing an internal property is essential. A security boundary or a real-time constraint may depend on how the program works, not only on the visible output. The question is which property the test is intended to establish.

I expect agents to improve at writing and maintaining tests. It may become relatively inexpensive to replace a program together with many of its checks. Teams will then benefit from understanding which commitments should remain independent of that replacement. The durable part of a system may be an account of what people can rely on, rather than the code through which the system currently keeps those promises.
